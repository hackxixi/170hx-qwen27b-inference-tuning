# 03 开发场景负载实测（2026-09-25）

通用 abbench 只测单轮问答。实际用得最多的是 Claude Code 这类 agent 客户端：长 system 前缀，加上多轮的工具调用和结果回填。所以这里单独做了一套开发场景负载，并用它比较四套配置。

**结论：** 在本仓库负载与硬件下，有并发时现役 HyperQwen 吞吐最高：8 并发聚合 137.9 tok/s，比 170hx-fullstack 原方案高 32%、比「推理栈 + HyperQwen 模型」高 18%（换个角度说，后两者慢 24% 和 15%）。单会话时，SGLang 推理栈加上我们的模型 decode 快约 7%，但会话耗时和现役持平。int8 输出头在开发场景下和现役持平。四套配置的工具调用函数名全部合法，JSON 参数不合法的都是撞到 `max_tokens` 被截断。

测试方法见 [00](00-methodology.md)；本轮基线是 A（int4 输出头）。

## 1. 负载设计

### 1.1 共享前缀
- Claude Code 的 system prompt + 14 个工具定义（Agent、Bash、Edit、Glob、Grep、Read、Skill、TaskCreate、TaskGet、TaskList、TaskUpdate、ToolSearch、Workflow、Write）+ 首条 user 消息里的上下文块（环境信息、目录说明等），合计约 23.0K token（vLLM 计 23,021 token；SGLang 的聊天模板多 365 token，计 23,386）。
- 8 条会话共享这段前缀，模拟一个 agent 客户端同时开多个任务。

### 1.2 会话

| 会话 | 语言 | 轮数 | 内容 |
|---|---|---:|---|
| s1-py-bugfix | 英 | 3 | 修 Python bug：SGLang HiCache L3 层的 LRU 文件淘汰逻辑 |
| s2-tool-grep-read | 英 | 7 | 工具驱动：在 HyperQwen 仓库里查 `MTP_DRAFT_VOCAB` 的处理逻辑并解释 |
| s3-rust-feature | 英 | 3 | 给 Rust 网关的 power-of-two-choices 负载均衡策略加功能 |
| s4-py-unittests | 英 | 3 | 给量化配置代码写 pytest 单测（mock 掉 vllm） |
| s5-zh-bash | 中 | 3 | 给推理服务启动脚本加 `--dry-run` 参数 |
| s6-tool-bash-test | 英 | 6 | 工具驱动：Rust 网关一致性哈希策略的单测失败，跑测试、找原因、修复 |
| s7-review-patch | 英 | 4 | 评审 SGLang radix cache 的 `pin_prefix` 补丁（引用计数、并发） |
| s8-zh-tool-rust | 中 | 6 | 工具驱动：排查网关熔断器半开状态放行过多的问题，中文作答 |

- 共 35 轮，其中 2 条中文、4 条含工具调用；s2 / s6 / s8 的轮次之间用 `tool` 消息回填预先准备好的工具结果。
- 会话素材取自 170hx-fullstack 与 HyperQwen 仓库里的真实源码和补丁。生成脚本 [`bench/gen_sessions.py`](../bench/gen_sessions.py) 需要这两个仓库的 checkout 作为外部输入，生成出来的 `workload.json` 不随本仓库分发。

### 1.3 录制与回放
- **录制（record）**：先在基线 A 上跑一遍，把它的回复（包括工具调用）作为所有配置共用的历史，写进 `transcript.json`。录制时 `max_tokens` 4096。
- **回放**：每轮的输入是 transcript 中这一轮之前的全部消息，所有配置看到的输入逐字相同；每轮 `max_tokens` 1500，贪心，关思考。
- **防串缓存**：首条 user 消息里有一个 `{NONCE}`，放在共享前缀之后。每个档位换一个 nonce，这样不同档位之间会话内容不会互相命中缓存，system + tools 前缀照常命中。
- **档位**：会话并发 c1 / c4 / c8。c1 是 8 条会话依次跑；c4 / c8 是 4 / 8 个会话同时跑，各自按轮次顺序推进。
- **其他模式**：`cold`（在 system 开头加唯一 nonce，让 system + tools + 上下文全部不命中，测冷启动首轮 TTFT）、`pin`（测 SGLang 的 pin_prefix）、`smoke`（冒烟）。

### 1.4 指标
- 聚合 tok/s：全部输出 token / 墙钟。
- 单轮 decode 中位：非工具轮的单轮 decode tok/s 中位数。
- TTFT 首轮 / 后续轮：会话第 1 轮 / 第 2 轮起的 TTFT 中位数。
- 前缀命中率：`cached_tokens / prompt_tokens`，分首轮和后续轮。
- 工具调用正确率：函数名是否在 14 个工具里、`arguments` 是否是合法 JSON、工具轮选的工具是否与 A 的录制一致、有没有把工具调用混进正文（泄漏）。

## 2. 四套配置
- **A**：现役（int4 输出头），vLLM 0.28。
- **D2**：int8 输出头（见 [02](02-int8-lm-head.md)），vLLM 0.28。
- **B**：170hx-fullstack 原方案，SGLang + DFlash2 + EfficientThink AWQ。
- **C′**：170hx-fullstack 推理栈 + HyperQwen 模型（见 [01](01-three-way-comparison.md) §1.2）。

四套都在同一节点的同一张卡上串行跑。

### 3.2 相对 A 的变化

| 配置 | c1 聚合 | c1 decode 中位 | c4 聚合 | c8 聚合 | c8 会话耗时 | c1 后续轮 TTFT | c8 后续轮 TTFT |
|---|---:|---:|---:|---:|---:|---:|---:|
| D2 | −1.5% | −0.2% | −5.1% | −1.4% | +1.3% | 0.73 → 0.74 | 1.21 → 1.34 |
| B | +4.4% | −4.7% | −3.3% | **−24.1%** | **+40%** | 0.73 → 0.51 | 1.21 → 3.43 |
| C′ | +10.0% | +6.8% | −5.9% | **−15.2%** | **+28%** | 0.73 → 0.51 | 1.21 → 2.05 |

- 开发场景的噪声带：c1 聚合 ±0.5%，c4 / c8 聚合 ±5%（[00](00-methodology.md) §4）。D2 的变化都在噪声带附近，和 A 持平。
- **8 并发**（在本仓库负载与硬件下）：A 比 B 高 32%、比 C′ 高 18%；会话耗时 55 s 对 77 s 和 71 s。原因和通用负载一样：DFlash2 block 8 每路验证 9 个 token，并发一高验证计算量就成了主要开销（见 [01](01-three-way-comparison.md) §2.5）。
- **单会话**：C′ decode 快约 7%（128 vs 120），聚合快 10%。SGLang 的后续轮 TTFT 更低（0.51 vs 0.73 s），但会话耗时和 A 持平（13.4 vs 13.8 s）。B 的单会话 decode 比 A 慢 5%，会话耗时中位 18.5 s。
- 各配置回放的是同一份历史，但每轮自己的输出长度不同：c1 下 8 条会话的输出总量 A 12,719 token、D2 13,448、B 13,781、C′ 14,503。聚合吞吐和会话耗时都受这个影响，单轮 decode 中位不受。
- **B 在 8 并发下后续轮 TTFT 到 3.43 s**，首轮反而只有 11.29 s（A 22.83 s）。推测是 SGLang 的调度优先处理新请求的预填充，后续轮排在后面（未验证）。

### 3.3 前缀缓存
- 首轮命中率 0.86–0.88：共享的 23K 前缀全部命中，首条消息里 nonce 之后的部分要预填充。
- 后续轮：vLLM 0.97，SGLang 0.99（c8 下 0.97）。两边都基本吃满。
- **冷启动**（system 开头加唯一 nonce，发各会话首轮；实测仍有约 1.25–1.36 万 token 命中，来源本轮未查明）：A 13.51 s（34,528 token，命中 12,528），D2 13.39 s；B 14.25 s（34,892 / 13,632），C′ 14.02 s。
- **SGLang 的 pin_prefix**：B / C′ 的 `/pin_prefix` 返回 200、`pinned_nodes=4`；vLLM 没有这个接口（404）。在这个负载上看不出 pin 带来的额外好处，因为前缀本来就一直是热的。

|---|---:|---:|---:|---:|---:|---:|
| A | 82 | 82（100%） | 79（96.3%） | 72 / 72 | 2 | 0 |

- 「与 A 选择一致」：A 录制里有工具调用的 72 个工具轮上，被测配置选了同一个工具的轮数。B 换了模型，4 轮选了不同的工具，这是模型差异，不是错误。
- JSON 参数不合法的全部是输出在 1500 上限处被截断：工具调用写到一半就停了。
- 代码块语法检查（回复里的 diff / python / bash / rust 代码块能否被解析）：A 30 块 27 通过，D2 31 / 26，B 19 / 16，C′ 28 / 23；没通过的一部分是截断（A 3、D2 2、B 5、C′ 5），其余是 bash 片段解析失败。

## 4. 录制时的 400 报错
- **现象**：第一次录制时，s1 在第 2 轮之后的回放报 HTTP 400。
- **根因**：录制用的 `max_tokens` 是 1500，A 在 s1 第 2 轮输出一个 Write 工具调用时撞到上限，`arguments` 只写了一半，是非法 JSON。这条不完整的工具调用被原样写进历史，下一轮回填给 vLLM 时，vLLM 解析历史里的 `tool_calls.arguments` 失败，直接拒绝整个请求（400）。
- **处理**：录制上限提到 4096；历史里仍然非法的 `arguments` 替换成 `"{}"` 并打印记录；HTTPError 时打印响应体，方便排查。
- **对客户端的建议**：
  - agent 客户端给模型的 `max_tokens` 要留够写完整个工具调用的余量（长文件的 Write / Edit 很容易超过 1–2K token）。
  - 客户端收到 `finish_reason=length` 且带有不完整工具调用时，不要把它原样放回历史；要么丢弃重试，要么提示模型分段写。
  - 网关或服务端在回填历史时，对非法 `arguments` 做容错（例如替换成 `{}`），而不是整条请求 400。

## 5. 过程记录
1. **生成负载**：`gen_sessions.py` 从 170hx-fullstack 仓库里的 Claude Code 请求样本取 system prompt 和 14 个工具定义（Anthropic 格式转 OpenAI function 格式），加上首条消息的上下文块，拼成共享前缀；8 条会话的用户消息和模拟工具结果按 §1.2 的任务类型手写。
2. **冒烟**：在一个生产副本上发 2 条：流式返回的 `tool_calls` 能正常解析；把工具调用按 `arguments` 字符串原样回填进历史后，下一轮能正常接受；共享前缀计 23,045 token，第 2 轮命中 22,464 token。
3. **SGLang 的 pin_prefix**：B / C′ 的 `/pin_prefix` 返回 `{"success":true,"pinned_nodes":4}`；vLLM 没有这个接口（404）。只发前缀的请求：A 命中 22,464 / 23,021 token，TTFT 0.51 s；刚起的 D2 没有缓存，TTFT 11.36 s；B / C′ 的 SGLang 在这个请求上不返回 `cached_tokens`，TTFT 12.0–12.4 s，说明 pin 之前前缀还不在缓存里。
4. **第一次录制撞上 400**：定位过程是先让 HTTPError 打印响应体，看到 vLLM 拒绝的是历史消息里的工具调用参数；再回看 transcript，发现 s1 第 2 轮的 Write 调用 `finish_reason=length`，`arguments` 停在半截。修法见 §4。
5. **调度调整**：原计划把 A / D2 放在一个节点、B / C′ 放在另一个节点并行跑，但 transcript 要在节点之间传递、两边的卡也不同，最后改为全部在同一节点的同一张卡上串行跑，保证可比。
6. **输入一致性核对**：逐轮比较各配置的 `prompt_tokens`（3 个档位 × 35 轮 = 105 轮）：D2 与 A 全部相同；B / C′ 全部比 A 多 365 token，来自 SGLang 的聊天模板差异，与会话内容无关。
7. **汇总**：`analyze_dev.py` 出 §3 的表，另外检查工具调用、代码块语法、泄漏；逐会话数据见 [data/raw-dev-4configs.md](data/raw-dev-4configs.md)。
