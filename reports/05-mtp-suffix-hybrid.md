# 05 MTP + suffix decoding 混合起草（2026-09-25，已否决）

**结论：** K 固定为 4，按 TRT-LLM 的方式用 suffix 草稿覆盖 MTP 草稿。通用负载单流快 0–10%，但在开发场景（本来要解决的就是这个场景）单会话慢 12%，4 / 8 并发慢 1–9%。所以不上线。第二步「放开 K」的前提是第一步收益 ≥10%，这个前提不满足，没有评估。

现有实现的调研、为什么选这种做法，见 [10](10-dflash2-and-hybrid-research.md) §3。测试方法见 [00](00-methodology.md)。

## 1. 设计
- suffix 部分用的是 [ArcticInference](https://github.com/snowflakedb/ArcticInference)（Apache-2.0）里的 `suffix_decoding` C++ 扩展（nanobind，不依赖 torch）。PyPI 上 0.0.6 以后只有 sdist，所以在镜像同版本的系统环境里单独编了这个子包（编译约 4 秒），用 PYTHONPATH 挂载，不装 entry point，不触发 Arctic 的 vLLM 插件。冒烟：10 万 token 的 prompt 建树 31 ms，一次 speculate 5.6 µs。
- 基于 vLLM 0.28 的 V1 GPUModelRunner 实现（生产镜像 684e927：async scheduling 开、`draft_sample_method=probabilistic`、FULL_AND_PIECEWISE graph、mamba align 模式）。新增 `vllm/v1/spec_decode/hybrid_suffix.py`，再在 `gpu_model_runner.py` 里加 3 处钩子，共 19 行，`HYBRID_SUFFIX=1` 时才启用：
  1. `__init__`：method 是 mtp 并且打开了开关，才构造 HybridSuffix；否则为 None，行为与原版一致。
  2. `sample_tokens`：采样之后、MTP 起草入队之前，在独立的 copy stream 上把 sampled_token_ids 拷回 CPU（D2H）到 pinned 环形缓冲，只等采样，不等起草。
  3. `propose_draft_token_ids`：batch 不超过 `MAX_BS`（默认 4）时，先等本步的 D2H 完成，在 CPU 上更新后缀树并做 speculate，再用 `index_copy_` 把满足阈值的行原地覆盖进 MTP 刚生成的草稿张量；batch 超过 `MAX_BS` 时只做非阻塞的历史同步，不覆盖。
- 概率采样的正确性：被覆盖行的 draft_probs 改成 one-hot（和 n-gram 草稿 q=1 的语义一样），rejection sampler 不改。
- 历史：每个请求自己维护输出序列（async 调度下 `token_ids_cpu` 里是 −1 占位）；局部树 = prompt + 输出，全局树 = 历史输出。
- 自匹配稀释：本步新 token 延后一步入树，避免 speculate 时树尾就是当前上下文的最后一段。
- 阈值（变体）：

  | 代号 | 含义 |
  |---|---|
  | off | `HYBRID_SUFFIX=0`，overlay 在但开关关，等于基线 |
  | never | 管线全开（D2H、建树、speculate 都做），永不覆盖。用来单测同步开销，贪心输出应与 off 逐字节相同 |
  | t4 | suffix 匹配长度 ≥4，且草稿满 K=4 才覆盖。这是 TRT-LLM `sa_spec_threshold` 的语义（最小匹配长度，默认 4） |
  | ema | suffix 期望接受数（前 K 个 token 累计概率之和）> 该请求 MTP 行接受草稿数的 EMA（α=0.3） |

## 2. 测试条件
- 另一个节点上的一张测试卡，生产同参（`--memory 14g`、不进网关），镜像 684e927（vLLM 0.28）。所有变体都和同机的 off 组比。
- 通用负载 abbench c1 / c8；开发场景 devbench c1 / c4 / c8（见 [03](03-dev-workload.md)）。never 在 abbench 只测了 c1，在 devbench 测了 c1 / c4。
- 顺序：off（含 gate、gate 复测 offb）→ never → t4（先带断言的 debug 版做 T>0 采样冒烟）→ ema → tf。

- **单会话（c1）全部为负**，而且覆盖行的接受数都低于 MTP 行（S < M）：suffix 在长上下文里匹配到了错误的续写。

- 并发档每一格只有少数几轮，单格的 ±20% 波动不足以下结论（开发场景并发档的单轮速率噪声见 [00](00-methodology.md) §4）。聚合吞吐在所有档位都没有超过 off。

- 「活跃步」是 batch ≤ `MAX_BS` 的步；「每活跃步等 D2H」是 propose 阶段等本步采样结果拷回 CPU 的时间。
- 全局看，t4 的覆盖行平均接受 2.81，比 MTP 行 2.11 高；覆盖行里 61% 是满接受（5209 / 8553）。但 MTP 行的平均接受数从 never 的 2.28 掉到 2.11：suffix 挑走的恰好是 MTP 本来也容易猜对的「照抄」段，剩给 MTP 的都是难猜的（推测）。所以「覆盖行 S 高」不等于「覆盖带来了净收益」。
- ema 覆盖得更多（31.7%），但覆盖行接受数更低（2.34），0 接受的覆盖行占 28%。

### 3.5 正确性
- **gate**：never 与 off 17/17 逐字节相同（off 自己的复测 offb 也是 17/17）。t4 1/17 全同，16 处分歧的 top1-top2 差都 ≤0.125。ema 1/17 全同，有 1 处差值 0.25（2 个 bf16 ulp），略超 0.125 的判据，其余 ≤0.125。
- **tf top1 一致率**：off 0.99510（= offb = never），t4 0.99523，ema 0.99498，都在噪声底之内。
- **概率采样冒烟**：带断言的 debug 版（检查覆盖行 draft_probs 为 one-hot）在 T>0 下跑完，无错误。

## 4. 原因
1. **每步都要等一次 D2H，约 13 ms**。批量小的时候，这一次同步就吃掉 3–7%：never 档（管线全开但不覆盖）c1 通用负载 −4~−5%、开发场景 −4%，全是这一项。
2. **长上下文里 4-gram 误匹配**。开发场景单会话约 3 万 token 的上下文里，4-gram 很容易匹配到错误的续写：c1 各类型 S 都低于 M，覆盖行里有 18%（t4）/ 28%（ema）一个都没猜中。
3. **MTP 本来就强**。MTP 在工具调用的 JSON 和照抄段上已经接近满接受（never 的 tool 类型 M = 3.21，满 4），suffix 能挑走的正好是 MTP 也容易猜对的部分，净收益被压缩。
4. **并发下偶有正收益，但不稳定**：MAX_BS=4 限制了覆盖只在 batch ≤4 的步生效，8 并发时只有 batch 回落时才覆盖。
5. 通用负载（c1 +7~+10%）和开发场景方向相反。推测是 abbench 的上下文短（几十 token 的 prompt 加自身输出），误匹配少，而代码、列表类输出里的自我重复能被 suffix 猜中（未单独验证）。

## 5. 过程记录

### 5.1 选型与打包
1. 三个镜像（vLLM 0.28 / 0.29 / 0.30）都自带 `vllm/v1/spec_decode/suffix_decoding.py`，但都没装 `arctic-inference`，纯 suffix 方法用不了。
2. PyPI 上 `arctic-inference` 0.0.6 以后只发 sdist，suffix 部分是独立的 C++（nanobind），不依赖 torch。在与生产镜像同版本 glibc（2.39）、同 Python（3.12）、g++ 13 的环境里单独编出 `_C.so`（约 4 秒），只打包 `arctic_inference/suffix_decoding` 这一个子包，用 PYTHONPATH 挂进容器，不装 entry point，所以不会触发 Arctic 的 vLLM 插件（插件会整体替换 model runner）。
3. 冒烟：10 万 token 的 prompt 建后缀树 31 ms，一次 speculate 5.6 µs，CPU 侧开销可以忽略。
4. 决定直接在生产用的 0.28（684e927）上做，不换 0.30：生产 MTP 走的是 V1 GPUModelRunner（不是 V2），async scheduling 开，`draft_sample_method=probabilistic`，FULL_AND_PIECEWISE graph，mamba align 模式。

### 5.2 设计评审后的修订
第一版设计经过一轮复核，改了四处：
1. **τ=4 的比较量**：第一版比的是「suffix 前 K 个 token 的累计概率之和 ≥4」。对照 TRT-LLM 文档，`sa_spec_threshold` 是「最小匹配长度」，默认 4。改成比较匹配长度，并要求草稿满 K；原来的累计概率写法保留为变体 `t4s`（`HYBRID_SUFFIX_GATE=score`），本轮没有上卡。
2. **自匹配稀释**：如果本步新采样的 token 立即入树，speculate 时后缀树的末尾就是当前上下文的最后一段，最长匹配总是「自己匹配自己」，得到的续写没有意义。改为本步新 token 延后一步入树。本地单测：让模型照抄 prompt 里的一段，score 为 4.0，52 步里 50 次覆盖、全部正确。
3. **增加 `never` 档**：管线全开（D2H、建树、speculate）但永不覆盖。一是验证钩子本身不改变输出（贪心应与 off 逐字节相同），二是单独量出同步开销。
4. **异步安全**：`sampled_token_ids` 的引用一直保留到本步 D2H 事件完成，避免张量被复用；pinned 覆盖缓冲只在等过本步事件后才写。

### 5.3 上卡
1. 原计划排在 decode 那条测试链后面用同一张测试卡，后来改到另一个节点的一张卡上，所有变体都和同机的 off 组比，不和 [04](04-decode-six-items.md) 的数字直接比。
2. 顺序：off（gate、gate 复测 offb、c1、c8、开发场景 c1 / c4 / c8）→ never（gate、abbench c1、开发场景 c1 / c4）→ t4（先用带断言的 debug 版做 T>0 采样冒烟，再 gate、c1、c8、开发场景各档）→ ema（同 t4）→ tf。
3. 开启调试统计后，每个变体输出活跃步、覆盖行数、接受分布、D2H 等待时间，就是 §3.4 的表。
4. 结论出来后删除测试容器、停内存守护，测试卡恢复为生产副本。
