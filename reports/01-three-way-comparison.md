# 01 三方案对比：HyperQwen vs 170hx-fullstack（2026-09-24）

对比对象：[170hx-qwen3.8-27b-fullstack](https://github.com/ChinaBoy0618/170hx-qwen3.8-27b-fullstack)。以下数字都是在本仓库负载与硬件下测得的，不代表该方案在其自身部署环境中的表现。

**结论：** 看速度，现役 HyperQwen 综合最优：中文、并发、长上下文都领先，只有英文单流落后 11–18%。看精度，只算量化误差的话，三套方案的理论差距在 1–2 dB 量级，实际用起来分不出来。170hx-fullstack 原方案真正多出来的变量是换了一个微调模型，而按它自带的评测，微调前后的差异也落在统计误差以内。**结论是不迁移。**

测试方法见 [00](00-methodology.md)，精度推算的完整过程见 [09](09-precision-theory.md)。

## 1. 三套方案

| | 现役 HyperQwen（代号 A） | 170hx-fullstack 原方案（代号 B） | 170hx-fullstack 推理栈 + HyperQwen 模型（代号 C′） |
|---|---|---|---|
| 引擎 | vLLM 0.28 + Marlin（[HyperQwen](https://github.com/syv-ai/HyperQwen) 684e927 补丁集） | SGLang v0.5.19 + 该项目自带补丁 | 同 B |
| 主模型 | Qwen3.8-27B W4A16 AutoRound（`-fast` 变体，int4 输出头） | EfficientThink（SFT+SimPO）AWQ W4A16 | A 的权重；lm_head、embed 反量化成 bf16，数值不变 |
| 投机解码 | MTP，k=4（每轮最多产出 5 个 token） | DFLASH，DFlash2 bf16 草稿，block 8（每轮最多 8 个） | 同 B |
| KV | bf16 | fp8_e4m3 | fp8_e4m3 |

### 1.1 测试条件
- 同一张 CMP 170HX，贪心解码，关思考，`max_tokens=900`。每组预热后跑 2 轮，取中位数。负载见 [00](00-methodology.md) §3.1。
- long4k / long32k 的输入长度按各自 tokenizer 计：A 为 4,179 / 33,203 token。

### 1.2 「推理栈 + HyperQwen 模型」为什么是 C′ 而不是 C
原计划的 C 是「SGLang 推理栈直接加载 HyperQwen 的 `-fast` 模型」，原样跑不起来：
1. **DFLASH**：DFlash2 的候选选择器要求目标模型的 lm_head 是 dense 权重，而 `-fast` 的 lm_head 是 int4 打包格式，启动即报错。
2. **改走 NEXTN（MTP）**：EAGLE 路径的 `get_embed_and_head` 报 `'ParallelLMHead' object has no attribute 'weight'`，同样是因为 lm_head 被量化了。
3. **C′ 的做法**：新建一个模型目录，其余文件 symlink 回 `-fast`，只把 lm_head（int4 → bf16）和 embed（int8 → bf16）反量化后另存。反量化只改存储格式，数值和 A 完全一致。
   - 只反量化 lm_head 时输出全是 `!!!`：日志报 `embed_tokens.weight_scale not found in params_dict`，SGLang 没按量化格式加载 int8 embed。把 embed 也反量化以后输出正常，开头与 A 逐字一致。
   - 反量化脚本：`mk-densehead.py`、`mk-denseembed.py`（未随仓库分发，逻辑就是按 group scale 反量化后写回 safetensors）。

### 1.3 与原方案部署的偏差项
- 关掉了 hicache、L3 缓存和 CC 前缀预热；没做 cpuset 绑核；没设 200 W 功耗墙（本仓库卡上是 250 W）。
- 这几项影响的是预填充、缓存命中和功耗，不影响 decode 速度。
- 聊天模板不同：SGLang 这套的 prompt 比 A 多 365 token（开发场景里实测，见 [03](03-dev-workload.md)）。

### 2.4 代码题与非代码题拆开看（c1 英文组，每路 decode 中位，两轮合计）

英文组 8 条里 4 条是写代码（Python / Go / Rust / SQL），4 条不是（TCP 原理、长江流域文章、金融危机总结、Transformer 说明）。

| | A | B | C′ |
|---|---:|---:|---:|
| 代码题 | 178 | 204 | 214 |
| 非代码题 | 146 | 138 | 151 |

- 代码题上 DFlash2 的长草稿优势最明显：B / C′ 比 A 快 15% / 20%。
- 非代码题上三者接近，B 反而比 A 慢 5%。非代码组里那条中文文章，B 只有 68 tok/s（A 110）。
- 所以英文单流的领先主要来自代码题；中文和一般说明文上没有优势。

### 2.5 原因
- **DFlash2 草稿的中文接受率只有约 23%**（英文约 43%），中文上每轮平均只多前进约 1.6 个 token（接受长度 2.6）。所以 SGLang 这套只在英文单流领先。
- **并发下验证开销吃算力**：block 8 每路要验证 9 个 token，MTP k=4 只验证 5 个。并发一上去，验证的计算量成倍增加，而 170HX 算力弱、又顶着功耗墙，k=4 的 MTP 在并发和中文上全面占优。见 [10](10-dflash2-and-hybrid-research.md) §2 的推算。
- **长上下文**：B / C′ 的 long32k TTFT 多 2.3–2.7 s，decode 慢 23–26%；fp8 KV 在 SGLang 上没有 vLLM 那种 graph 退化（对比 [08](08-kv-cache-quantization.md)），这里的差距推测主要来自接受长度（long32k 只有 2.4–2.5，A 为 3.05）。
- **原方案 README 自报的 218–300 tok/s 在本环境未能复现**（测试条件可能不同，例如本测试关闭了其缓存与预热组件）。本环境同栈实测的英文单流是 177–188，代码题单条（两轮均值）最高约 254。

### 2.6 稳定性
252 条请求，0 错误，0 Xid（GPU 驱动报错）。输出质量粗检（每条请求）：A 76 条正常、8 条有长重复字符段；B 76 / 8；C′ 75 / 9。被标记的都是代码缩进之类的正常重复。

逐档原始数据见 [data/threeway-analysis.md](data/threeway-analysis.md)。

### 2.7 原始数据
逐轮（r1 / r2 与中位）的每路、聚合、TTFT、输出 token、接受长度、接受率，以及 c1 的逐条数据，见 [data/raw-threeway.md](data/raw-threeway.md)。两轮之间的差异：A 各档聚合在 ±3% 以内，B / C′ 也在 ±3% 以内。

## 3. 精度：理论误差推算
完整推导见 [09](09-precision-theory.md)，这里只列结论。

| 格式（group=128 数值模拟） | 高斯 | 厚尾 t5 |
|---|---:|---:|
| int4 对称（现役主体 / lm_head / MTP） | 11.1%（19.1 dB） | 16.2%（15.8 dB） |
| int4 非对称（原方案主体） | 10.1%（20.0 dB） | 13.3%（17.5 dB） |
| int8 对称（现役 embed、原方案 33 个敏感模块） | 0.65% | 0.95% |
| fp8 e4m3（KV） | 2.65%；绝对值小于约 0.02 时升到 5.7% | — |
| bf16 | 0.17% | — |

1. **主体权重**：原方案的非对称网格误差小 9%–18%，另外把 33 个敏感模块（约 2.4B 参数）留在 int8。合计噪声能量约为现役的 0.61–0.74，RMS 低 14%–22%，信噪比高约 1.3–2.2 dB。AutoRound 的逐层误差最小化一般比 AWQ 好，会抵消一部分。
2. **lm_head（两者差距最大的一项）**：现役 `-fast` 把 1.27B 参数的输出头压到了 int4，基座版原本是 int8，原方案是 bf16。候选之间差值的噪声约 0.15–0.5 nats，只有 top1 和 top2 差距小于约 0.5 nats、top1 概率约 0.6 以下的「分岔 token」可能被翻转。这个推算后来在 [02](02-int8-lm-head.md) 里得到了实测印证（分歧点 top1 概率 0.17–0.60）。
3. **KV cache**：fp8 只作用于 64 层中的 16 层全注意力层，总噪声能量 +1.5%，RMS 约 +0.7%。
4. **投机解码**：贪心下输出就是目标模型的 argmax，采样时用拒绝采样，理论无损。
5. **微调（只有原方案有）**：GPQA +3.5（标准误 3.6）、MMLU −1.8（1.95）、LiveCodeBench +5（6.4），三项都在约 1σ 以内，统计上不显著。评测是开思考、动态 FP8 做的，关思考时没有数据。

**汇总**：理论保真度原方案 ≳ 现役 ≈ 推理栈 + HyperQwen 模型，差距 1–2 dB 量级。现役要补精度，最划算的是把 lm_head 换回 int8，代价是每步多读约 0.6 GB 权重，结果见 [02](02-int8-lm-head.md)。

## 4. 更早的测试（2026-09-18，原始记录未收录）
- **TP=2 跨两卡**：单流 24–36 tok/s，8 并发 42 tok/s，比单卡慢 6–9 倍。原因是 PCIe Gen2，且卡间没有 P2P，每层的 all-reduce 都要绕主机内存。
- **上游默认的 40k 截断草稿词表**：按丹麦语、英语和代码统计，中文 token 基本不在表里（held-out 中文覆盖率 35.6%）。改成全词表起草（`MTP_DRAFT_VOCAB=0`）后，中文单流从 68 升到 127 tok/s，中文 8 并发从 210 升到 419，英文不降反升。
- **`DRAFT_TOKENS` 4 对 6**：单流持平，8 并发下 k=4 高 16–23%，所以定为 k=4。

## 5. 过程记录

### 5.1 准备
1. **读对方仓库**：README、部署文档、AWQ 启动脚本、Dockerfile、模型清单，确认它的完整栈是 SGLang v0.5.19 + 自带补丁 + EfficientThink AWQ + DFlash2 草稿 + fp8 KV。
2. **镜像**：对方 Dockerfile 以 `lmsysorg/sglang:v0.5.19-cu130` 为底。本机已有这个基础镜像，而且对方第一组补丁涉及的 11 个文件与镜像内的 md5 完全一致，所以直接把 `FROM` 指向本地镜像构建，关掉 BuildKit（`DOCKER_BUILDKIT=0`）。
3. **模型**：下载 EfficientThink AWQ W4A16（约 20 GB）和 DFlash2 bf16 草稿（约 3.6 GB）。草稿的 sha256 与 ModelScope 上 FP8 包 manifest 里记录的 bf16 源文件 sha256 一致。各模型的量化配置（`config.json` 的 `quantization_config`、ignore 列表）逐项抄下来做对比，这是 §3 精度推算的输入。
4. **长输入校准**：long4k / long32k 的 token 数用现役服务的 `/tokenize` 校准（4,179 / 33,203）。

### 5.2 测试
1. 停下测试卡上的生产副本，按 A → B → C 的顺序各起一个测试容器，跑完即删。
2. **A**：生产同参，测速正常。
3. **B**：SGLang 启动约 576 s（含 CUDA graph 捕获），容器常驻内存约 10 GB，宿主可用内存一度掉到 5 GB。为防止挤爆同机的其他服务，另起一个守护脚本，可用内存低于 2.5 GB 时自动杀掉测试容器（全程没有触发）。
4. **C：HyperQwen 模型原样上 SGLang，两种投机方式都失败**：
   - DFLASH：引擎启动后第一次前向就退出，报错原文：
     `RuntimeError: DFlash2 selector requires a dense FP16/BF16/FP32 target lm_head or a supported lm_head.quant_method.`
     原因是 `-fast` 的 lm_head 是 int4 打包格式（compressed-tensors pack-quantized），DFlash2 的候选选择器要直接读目标模型的 dense lm_head 权重。
   - 改走 NEXTN（用模型自带的 MTP 头，走 SGLang 的 EAGLE 路径）：启动分配显存池时失败，报错原文：
     `AttributeError: 'ParallelLMHead' object has no attribute 'weight'`
     出在 `qwen3_5.py` 的 `get_embed_and_head()`，同样是因为量化后的 lm_head 没有 `.weight`。
5. **C′：把 lm_head 反量化成 bf16**：
   - 新建模型目录，其余文件 symlink 回 `-fast`，只把 lm_head 按 group scale 反量化成 bf16 另存。
   - 第一次只反量化 lm_head：服务能起来，但输出全是 `!!!`。日志里有 `embed_tokens.weight_scale not found in params_dict`：SGLang 没按量化格式加载 int8 的 embed，拿到的是未缩放的整数值。
   - 把 embed（int8 → bf16）也反量化后输出正常，开头与 A 逐字一致，确认数值没变。
   - 接受长度 2.4–4.0，用 `/metrics` 计数和服务端日志里的投机统计交叉核对过，一致。
6. 测完恢复生产副本：停机约 60 分钟，恢复后 `/health` 200，经网关发 34 条请求全部 200。

### 5.3 DFlash2 草稿的中文接受率为什么低
- 数据：B 与 C′ 的目标模型不同（EfficientThink 与 HyperQwen），但中文接受率都是 0.22–0.25，英文都是 0.38–0.43。说明这是草稿模型本身的特性，与目标模型无关。
- 同一个目标模型（C′ 与 A 数值相同）上，模型自带的 MTP 头中文接受率 0.46–0.48。MTP 头是和目标模型一起训练的，覆盖了目标模型的全部语种；DFlash2 是外挂的独立草稿。
- 逐条看（[data/raw-threeway.md](data/raw-threeway.md)），DFlash2 在代码题上最强（单条两轮均值最高约 254 tok/s），在中文长文上最弱（英文组那条中文文章 B 只有 68 tok/s）。
- 草稿模型的说明文档没有写训练语料的语种构成。结合上面的数据，推测它的训练数据以英文和代码为主（未验证）。

## 6. 复现
- 测速脚本：[`bench/abbench.py`](../bench/abbench.py)，汇总脚本：[`bench/analyze_threeway.py`](../bench/analyze_threeway.py)。
- long4k / long32k 用的是约 4.2k 和 33k token 的中文长文档，文档本身不随仓库分发，可以换成任意同长度的材料。
- 代码题拆分：读 abbench 的 c1 输出 JSON，取英文组两轮里每条请求的 `decode_tps`，按下标 0、3、5、7（代码）与 1、2、4、6（非代码）分组取中位数。
