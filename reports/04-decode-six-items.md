# 04 decode 提速各项实测（2026-09-25）

**结论：** 只有「组合版」（vLLM 0.30 + int4 起草头）有明显正收益：通用负载快 5–9%，开发场景单会话 decode 快约 10%，贪心输出和基线等价，已上线（见 [06](06-canary-and-rollout.md)）。会话粘滞路由对开发场景首字延迟的改善最大，单独写在 [07](07-session-affinity-routing.md)。截断草稿词表、KV int8 / fp8（单独写在 [08](08-kv-cache-quantization.md)）、绑核和提优先级都没有收益。

## 测试条件
- **测试卡**：一张从生产里临时摘下来的 170HX，测试容器单独起，不进网关。测试期间曾因外部供电中断，受影响的轮次整体作废重测。
- **基线 P**：int8 输出头上线后的生产配置。HyperQwen 684e927（vLLM 0.28）、MTP k=4、int8 输出头（见 [02](02-int8-lm-head.md)）、全词表起草（`MTP_DRAFT_VOCAB=0`）、KV bf16。
- **负载、正确性判据、噪声带、GPU 采样**：见 [00](00-methodology.md)。本轮噪声带：通用负载 ±2%，开发场景 c1 ±0.5%、c4 / c8 聚合 ±5%；贪心 P 与 P3 17/17 全同；P 自比 tf 99.51%。
- **测试顺序**：P → D3 → V32 → V48 → V64 → V029 → V030 → CS → CSN → C1 → KI8 → KF8 → tf 专用容器（TFP / TFI / TFK）→ P3（收尾复测）。

## 各项说明

### int4 起草头（D3）
- 背景：换成 int8 输出头以后，MTP 起草也跟着读 int8 头（vLLM 的 proposer 会共享目标模型的 lm_head）。每步 k=4 次起草都要多读一份 int8 头的权重。
- 做法：模型目录里另存一份 `mtp.draft_head4.*`，内容就是 `-fast` 原来的 int4 lm_head（多 626 MB）；再打一个补丁，让 MTP 的 `compute_logits` 读这份权重（`MTP_DRAFT_HEAD4=1` 时生效）。目标模型验证仍然用 int8 头。所以最终输出只由 int8 头决定，起草头只影响接受率。补丁见 [`patches/d3-draft-head4/`](../patches/d3-draft-head4/)。
- 启动日志确认：draft_head4 形状是 (248320, 640)，int4 打包；验证用的 lm_head 是 (248320, 1280)，int8。
- 精度：贪心 2/17 全同，15 个分歧点上基线侧的 top1-top2 差值全部 ≤0.125 nats，没有一处 ≥0.25。probe 9 : 6，差距中位 0.000。tf 一致率 99.48%（13,186 / 13,255），和噪声底 99.51% 持平。判定为数值抖动，等价。
- 这个补丁对 vLLM 0.29 / 0.30 的 `qwen3_5_mtp.py` 都能打上（偏移 2–10 行）。

### 截断草稿词表（V32 / V48 / V64）

  | 英文 | 94.9% | 90.6% | 93.8% | 95.8% |
  | 开发场景中文 | 70.4% | 83.8% | 88.9% | 91.4% |
  | 开发场景英文 | 96.1% | 89.1% | 93.5% | 96.2% |

- 截断后覆盖缺口 3–23%，接受长度下降 0.1–0.4（英文 3.43 → 3.04 / 3.15 / 3.23，long32k 3.20 → 2.82 / 2.93 / 3.01），省下来的那点起草头读取量补不回来。理论上限的推算见 [10](10-dflash2-and-hybrid-research.md) §4：整个起草头的读取开销只占 2–4%。
- 现役本来就是全词表起草，所以不上。

### cpuset / nice（CS / CSN）
- CS：`--cpuset-cpus` 绑到卡所在的 NUMA 节点。CSN：在 CS 基础上把容器内全部线程（195 个）设成 nice −10。
- 通用负载的变化在 −0.9%~+0.9% 之间，开发场景 c1 持平，贪心输出 17/17 全同。CS 实际上等于又做了一次 P 复测。
- 根因是瓶颈在 GPU 功耗墙：除 KV 两项外，所有变体测试时约 95% 以上的忙碌采样都触发了 SW Power Cap，功率中位 246–249 W（墙是 250 W），SM 时钟中位 1350–1395 MHz（上限 1695），显存时钟 1728 MHz 满频。
- 唯一可能的硬件杠杆是把功耗墙从 250 W 调到上限 300 W。本轮没有调，也没有测。

### vLLM 0.29 / 0.30（V029 / V030）
- 0.29 是 HyperQwen 73fd65d 自带的版本。0.30 是自建镜像：以 0.29 镜像为底，装上 vllm 0.30.0，再应用 [HyperQwen PR#189](https://github.com/syv-ai/HyperQwen/pull/189) 的补丁系列（截至 2026-09-25 该 PR 尚未合入）。同一模型、同一套参数。
- 两个版本跨版本贪心分别有 2/17 和 0/17 全同，分歧点差值 ≤0.25，都是数值级分歧。
- 0.30 的 KV 池是 528,901 token，比 0.28 的 556,584 略少。

### 组合版（C1）
- vLLM 0.30 + D3 模型目录 + int4 起草头补丁（0.30 版）。启动日志确认 draft_head4 int4 (248320, 640)、验证头 int8 (248320, 1280)。
- 通用负载全面 +5~9%，开发场景 c1 decode +9.7%、c1 聚合 +2.3%、c8 聚合 +3.5%、c4 聚合 −1.6%（后两者在噪声带内）。接受长度持平。
- 精度：贪心 2/17 全同，分歧位差距 ≤0.25（有一处 C1 侧 0.375），probe 11 : 4 选 C1 侧（差距中位 0），属数值级。
- 上线过程见 [06](06-canary-and-rollout.md)。

### 准备
1. **勘察**：确认生产已是 int8 输出头（`hq.env` 指向 `-fast-head8`），D3 目录的 `config.json` 与生产 `-fast-head8` 的 md5 相同，D3 = P 的全部文件 + 一个 626 MB 的 `model_draft_head4.safetensors` + index 里多 3 个键。
2. **脚本**：测试容器启动、整套测试（gate → abbench 各档 → devbench 各档 → GPU 采样）、内存守护、gate / tf / probe、草稿词表生成，全部放到测试节点上，串成一条链自动跑。
3. **镜像**：vLLM 0.29 用 HyperQwen 73fd65d 自带的镜像。vLLM 0.30 没有现成镜像，本地以 0.29 镜像为底，装 vllm 0.30.0，再按 [PR#189](https://github.com/syv-ai/HyperQwen/pull/189)（ef0fd4b）的 series 打补丁，跑补丁自带的 verify 通过后，导出传到测试节点（约 40 分钟）。
4. **前缀缓存路径复现（Pb）**：原计划用 `/reset_prefix_cache` 清缓存再跑一遍 gate，但这个接口返回 404。改为不清缓存直接再跑一次 gate（走前缀缓存命中的路径），与 P 比 17/17 全同，说明缓存命中与否不改变贪心输出，后续比较不需要特意清缓存。

### 第一次开场作废
- 第一张测试卡上 P 跑完全套后，在生成自有输出（给草稿词表统计用）时遇上外部供电中断，节点重启，测试链中断，自有输出只救回 110 条。
- 这张卡恢复后要优先回到生产，之后不再用作测试卡。整轮换到另一张测试卡，从 P 重新开始；旧卡上的 P 数据作废，不进任何表。

### int4 起草头（D3）的硬门：2/17 全同如何判定为数值抖动
gate 只有 2/17 逐 token 全同，按规则要进一步判定是补丁 bug 还是数值抖动。依次查了四项：
1. **分歧点差值**：15 个首分歧位上，P 侧 top1-top2 差全部 ≤0.125 nats，没有一处 ≥0.25。bf16 logprob 的分辨率就是 0.125，这些是真平局。
2. **probe**：在分歧前缀上让 P 自己走 prefill 路径重选 1 个 token，结果 9 次选 P 的 token、6 次选 D3 的，差距中位 0.000。也就是说 P 自己换一条计算路径，也会在这些位置翻。
3. **启动日志核对形状**：`draft_head4` 的 weight_packed 是 (248320, 640)，即 int4；MTP 自身与验证用的 lm_head 是 (248320, 1280)，即 int8。验证确实用的 int8 头，补丁只改了起草。
4. **tf**：D3 对 P 的贪心输出 13,186 / 13,255 = 99.48%，P 自比噪声底 99.51%，差 0.03 个百分点。
四项都指向数值抖动，判定等价。

### 截断草稿词表的构建
1. 语料：自有输出 419 条（旧卡救回 110 条 + 新卡 6 分钟生成 309 条）+ GPT-4 指令语料的中文、英文、代码三部分，混合做 token 频数统计。
2. 取频数前 32k / 48k / 64k 的 token，从 int8 lm_head 里按行切片，存成 `draft_lm_head`（形状 (N, 1280)），模型目录用 symlink 组装成 V32 / V48 / V64。
3. held-out 覆盖率用的是往轮测速和开发场景的输出，不参与计数（见上面的覆盖率表）。
4. 截断后起草头更小，但覆盖缺口让接受长度下降，净效果为负。

### cpuset + nice（CSN）的一个坑
测试脚本里自带的 `renice` 在宿主上执行时用错了 PID 命名空间，没有生效。发现后在 gate 之后、c1 之前手工对容器内全部 195 个线程设了 nice −10，所以测速段全部生效；gate 本身不受 nice 影响。

### 组合版（C1）
- vLLM 0.30 的 `qwen3_5_mtp.py` 与 0.28 有差异，D3 补丁在 0.29 / 0.30 上都能打上（偏移 2–10 行），另存为 0.30 版补丁挂载进容器。
- 测完 C1 后先看启动日志的三个标记（`head8-d3`、`v0.30`、`separate draft_head4`），后来滚动上线脚本就用这三个标记做自检。

### 收尾
全部测试容器删除，内存守护停止；测试卡恢复为生产副本。收尾复测 P3 与开场 P 贪心 17/17 全同，通用负载差 −0.9% ~ +1.8%，据此定出噪声带（[00](00-methodology.md) §4）。
